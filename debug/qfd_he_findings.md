## 1. What the path actually is

The 0.19 %-at-`n_max=7` headline (Paper 13) comes from
`geovac.casimir_ci.build_graph_native_fci(Z, n_max, m_total, spin)`, **not** from
`lattice_index.LatticeIndex` — the latter uses the chordal/Mulliken `V_ee`
approximation and is a different object. `build_graph_native_fci` is the
zero-parameter hybrid: exact one-body diagonal, graph-Laplacian one-body
off-diagonal, analytic Slater `V_ee`.

Ingredient-by-ingredient audit of that route:

| ingredient | source | exactness |
|:--|:--|:--|
| one-body diagonal `-Z²/(2n²)` | `_build_graph_h1` | **rational** |
| one-body off-diagonal `κ·(-A_ij)` | `GeometricLattice.adjacency`, `κ = -1/16` | **rational** — the default lattice is `topological_weights=False`, so `A` is strictly binary (asserted in the new module); every edge contributes exactly `+1/16` |
| radial Slater `R^k` | `_RK4_TABLE`, else `hypergeometric_slater.get_rk_float` | **rational** (the table is hard-coded `Fraction`s; the fallback has an exact-`Fraction` twin, `compute_rk_algebraic`) |
| orbital-exponent scaling `k_orb = Z` | `two_electron_integral` | **integer** |
| Gaunt `c_k` | `_gaunt_ck` / `_wigner3j` | **algebraic** — each is `(rational)·√(rational)` |
| symmetrisation `1/(N_IJ N_PQ)` | `build_graph_native_fci` | **algebraic** — `1`, `1/√2` or `1/2` |

So **every matrix entry lies in a real field generated by square roots of
rationals, and the ground-state eigenvalue is an algebraic number.** There is no
quadrature in the route. The production code is float-only (it casts `Fraction`
→ `float` and computes 3j symbols in float64); the *formulas* are exact, which
is what makes a high-precision rebuild possible.

Two float-only fallbacks exist in `casimir_ci` but are **not reached** on this
path: `_compute_inv_r_numerical` (only used when `k_orb ≠ Z`; the graph-native
builder sets `k_orb = Z` and the one-body matrix comes from `_build_graph_h1`
instead), and `_compute_rk_numerical` (superseded by the
`hypergeometric_slater` dispatch).

## 2. Route used

**Exact assembly + one rounding.** New module
`benchmarks/certified_reference/entries_helium.py` re-assembles the same matrix
with every ingredient kept exact: Wigner 3j as `(sign, S, P)` with
`W = sign·S·√P` and `S, P` exact `Fraction`s from integer factorials; `R^k` from
`compute_rk_algebraic` (exact `Fraction`, any `n`); each entry stored as
`(rational part, {radicand: rational coefficient}, normalisation)`. The matrix is
rounded to `mpf` **once**, at the working precision, then diagonalised.

This is the *exact-arithmetic* route at every `n_max` — not an "mpmath rebuild of
a float formula". No `n_max` needed the weaker route, so the BORDERLINE branch of
the gate was not used.

At `n_max = 1` the singlet `M_L = 0` sector holds one configuration (1s²), so the
matrix is 1×1 and the energy is the **exact rational**
`E = -Z² + 5Z/8 = -11/4` at `Z = 2`. Published as `digits_claimed = "exact"`.

**Eigensolver.** Two, cross-checked:

* `ground_state_mp_lu` — Rayleigh-quotient iteration with full O(n³)
  arbitrary-precision LU factorisations. Correct but slow: it did not finish
  `n_max = 5` (dim 266) inside ~25 min and was abandoned for routine use.
* `ground_state_mp` — float64-preconditioned residual refinement. The correction
  equation `(H-λ)δ = -r, δ ⊥ v` is solved in the **float64** eigenbasis, so an
  iteration is O(n²) instead of O(n³) and the inexact preconditioner costs
  convergence *rate*, never correctness. 10× faster at dim 101, and it turns
  `n_max = 5` into ~16 s of diagonalisation.

The two agree to full working precision (≈1e-75 at dps 75) at `n_max = 2, 3, 4`;
that agreement is recorded per entry as `lu_agree_digits` wherever dim ≤ 120.

## 4. Evidence per entry

1. **Two-precision agreement** — the whole assemble-and-diagonalise route at
   dps 55 and dps 75: **55 digits** agreement at every `n_max` (capped at
   `dps_lo`; the claim is then capped at 35).
2. **Rigorous residual bound** — for symmetric `H` and normalised `v`,
   `|λ_min − vᵀHv| ≤ ‖Hv − λv‖`. Measured `2.8e-76 … 1.1e-75` — independent of
   how the eigenvector was found. Carried back to the *exact* matrix by the
   rounding perturbation `n·max|H_ij|·10^(1-dps) ≤ 7.3e-52` at dps 55. Both are
   ~17 orders below the 35-digit claim.
3. **Second eigensolver** (dim ≤ 120) — LU-based RQI on the same exact matrix
   agrees to **75 digits** (i.e. to working precision) at `n_max = 2, 3, 4`.
   Not run at `n_max = 5` (dim 266): it is O(n³) at arbitrary precision and did
   not finish; that entry rests on checks 1, 2, 4 and 5.
4. **Float-pipeline cross-check** — the production route
   (`build_graph_native_fci` + `numpy.linalg.eigvalsh`) reproduces every value:

   | n_max | production float64 | relative agreement |
   |--:|:--|:--|
   | 1 | `-2.75` | exact cast |
   | 2 | `-2.8894787019709858` | 7.98e-17 |
   | 3 | `-2.8931097422339302` | 6.24e-16 |
   | 4 | `-2.895405560697803` | 7.30e-16 |
   | 5 | `-2.896475793482457` | 5.10e-17 |

   All at the float64 round-off floor, ~4 orders inside the 1e-12 STOP gate.
5. **Category-wide integral check** — all **145** hard-coded rational Slater
   integrals in `casimir_ci._RK4_TABLE` were re-derived from
   `hypergeometric_slater.compute_rk_algebraic`: **0 mismatches**. This is what
   rules out a transcription error in the table feeding every entry.

## 5. Honest framing (carried in the artifact, not just here)

These certify the **assembly**, not the accuracy. The physical non-relativistic
infinite-mass helium ground state is `-2.903724377034119598` Ha (Pekeris/Drake);
the tabulated values sit **5.29 % / 0.491 % / 0.366 % / 0.287 % / 0.250 %** above
it at `n_max = 1…5`. Thirty-five certified digits are thirty-five digits of a
*truncated-basis eigenvalue whose first two digits already differ from helium*.
Every entry's `evidence` field says this explicitly (`SCOPE — this certifies the
ASSEMBLY, NOT the accuracy…`), the category blurb repeats it, and two tests
enforce that the caveat and the Pekeris comparison stay attached.

The comparison is also the reason the series is worth publishing: it is the
convergence curve of the construction, in exact arithmetic, reproducible to 35
digits by anyone reimplementing it.

## 6. One incidental defect found (not in production)

`casimir_ci._wigner3j` computes its phase as `(-1) ** (j1 - j2 - m3)`. For a
negative exponent Python returns a **float** `±1.0`, not an int. In the float
pipeline this is numerically harmless (the value is right), but it silently
poisons any exact-arithmetic reuse of the same expression — it turned
`Fraction` accumulators into floats in the first draft of the new module. The
new module uses an integer parity test instead. **No production change made**;
recording it here because the next exact-arithmetic reuse of `casimir_ci` will
hit it.
